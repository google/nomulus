# Brand Safety Alliance (BSA) Integration

This package implements the integration between Nomulus and the Brand Safety
Alliance (BSA). The integration protects trademark holders and brand owners by
preventing registrations of domain labels that match active BSA block orders
across all BSA-enrolled top-level domains (TLDs).

## Architectural Overview

The BSA subsystem is comprised of four primary scheduled actions that run as
cron tasks on the `backend` service:

1. **`BsaDownloadAction`** (`/_dr/task/bsaDownload`): Downloads the latest block
   lists from BSA, computes incremental diffs against the previous download,
   updates local database tables, and sends order status and unblockable domain
   reports to BSA.
2. **`BsaRefreshAction`** (`/_dr/task/bsaRefresh`): Periodically detects domain
   lifecycle changes (new domain registrations, cancellations/deregistrations,
   and reserve list modifications) that affect blockability, updates the
   database, and syncs unblockable domain changes to BSA.
3. **`BsaValidateAction`** (`/_dr/task/bsaValidate`): Validates database records
   against raw GCS block lists, active domain registrations, and reserved lists,
   alerting operators to any discrepancies.
4. **`UploadBsaUnavailableDomainsAction`**
   (`/_dr/task/uploadBsaUnavailableNames`): Compiles a comprehensive snapshot of
   all unavailable domains (registered and reserved) across all BSA-enrolled
   TLDs and uploads a gzipped list with a SHA-512 checksum directly to BSA.

A shared distributed lock (`BsaLock`, lock name `all-bsa-jobs`) prevents race
conditions between concurrent download and refresh actions.

## 1. Format of Downloaded Data Files

Data files are retrieved from BSA via HTTPS `GET` requests using Bearer token
authentication (`BsaCredential`). Two block list product types are downloaded
as defined in `BlockListType`:

*   **`BLOCK`**: Standard block list (`BLOCK.csv`).
*   **`BLOCK_PLUS`**: Extended block list (`BLOCK_PLUS.csv`).

### HTTP Stream Wire Format

The raw response returned by the BSA server contains an inline checksum on the
very first line:

1.  **Line 1 (Inline Checksum)**: A hexadecimal hash string generated by BSA
    (terminated by whitespace/newline).
2.  **Subsequent Lines (CSV Content)**: The actual block list CSV payload.

`BlockListFetcher` consumes the first line as the expected checksum and streams
the remaining CSV payload to Google Cloud Storage (GCS).

### GCS File Format

The downloaded files are saved in GCS under a job-specific folder:
`gs://<bsaGcsBucket>/<jobName>/BLOCK.csv` and `BLOCK_PLUS.csv`. The folder name
`<jobName>` is derived from the download creation timestamp formatted as
`yyyy-MM-dd't'HHmmss.SSS'z'` (e.g., `2026-10-27t170020.076z/`).

Both files adhere to the following CSV structure (UTF-8 encoded):

*   **Header line**:
    ```csv
    domainLabel,orderIDs
    ```
*   **Data lines**:
    Each row contains a second-level domain (SLD) label and a
    semicolon-delimited list of 64-bit integer order IDs:
    ```csv
    <domainLabel>,<orderID_1>[;<orderID_2>;...]
    ```

### Example Entries

From `gs://domain-registry-bsa/2026-10-27t170020.076z/BLOCK.csv`:
```csv
domainLabel,orderIDs
1177,1143802407471
acaminetti,1632899805171
accenture,9111676114371
achotels,798607544371
```

From `gs://domain-registry-bsa/2026-10-27t170020.076z/BLOCK_PLUS.csv`:
```csv
domainLabel,orderIDs
1-occitane,8035826110371
anfie1d,2857366171871;6228091912971
anfield,2857366171871;6228091912971
```

### Checksum Verification and NOP Handling

While streaming the CSV payload to GCS, `GcsClient` computes the message digest
using the configured algorithm (`bsaChecksumAlgorithm`, e.g., SHA-256):

*   **Checksum Mismatch**: If the locally computed checksum does not match the
    inline checksum provided on line 1 by BSA, the download is aborted and
    check-pointed with stage `CHECKSUMS_DO_NOT_MATCH`.
*   **Unchanged Checksums (NOP)**: If the checksums match those from the most
    recently completed job, and elapsed time has not exceeded
    `bsaMaxNopInterval`, the download processing is skipped with stage `NOP`.

## 2. Format of Intermediate Files Generated

During download and refresh executions, intermediate and report files are
written to GCS. Intermediate files persist processing states across stage
transitions, while JSON files log the exact payloads submitted to BSA REST API
endpoints.

### Files Generated During Download Processing (`BsaDownloadAction`)

Folder: `gs://<bsaGcsBucket>/<downloadJobName>/`
(e.g., `gs://domain-registry-bsa/2026-10-27t170020.076z/`)

1.  **`orders_diff.csv`**:
    *   **Description**: Order-level changes computed by `BsaDiffCreator`.
    *   **Format**: Headerless CSV; `<orderId>,<orderType>`.
    *   **Types**: `CREATE` (new order) or `DELETE` (removed order).
    *   **Example**:
        ```csv
        2431667113971,CREATE
        ```

2.  **`labels_diff.csv`**:
    *   **Description**: Label-level changes computed by `BsaDiffCreator`.
    *   **Format**: Headerless CSV; `<label>,<labelType>[,<idnTable>...]`.
    *   **Types**: `CREATE`, `NEW_ORDER_ASSOCIATION`, or `DELETE`.
    *   **Trailing columns**: Sorted list of IDN table names supporting the
        label.
    *   **Example**:
        ```csv
        waymo,CREATE,EXTENDED_LATIN,JA,UNCONFUSABLE_LATIN
        ```

3.  **`unblockable_domains.csv`**:
    *   **Description**: Domains matching added labels that cannot be blocked
        because they are already registered or reserved.
    *   **Format**: Headerless CSV; `<domainName>,<reason>`.
    *   **Reasons**: `REGISTERED`, `RESERVED`, or `INVALID`.
    *   **Example**:
        ```csv
        waymo.day,REGISTERED
        waymo.ing,RESERVED
        waymo.app,RESERVED
        waymo.dev,RESERVED
        waymo.new,RESERVED
        waymo.page,RESERVED
        ```

4.  **`in_progress_orders.json`**:
    *   **Description**: Sent to BSA (`bsaOrderStatusUrl`) declaring that
        order processing has begun.
    *   **Format**: JSON array of objects with `blockOrderId` (number) and
        `status` (`"ActivationInProgress"` for new orders or
        `"ReleaseInProgress"` for deleted orders).
    *   **Example**:
        ```json
        [
          {
            "blockOrderId": 2431667113971,
            "status": "ActivationInProgress"
          }
        ]
        ```

5.  **`added_unblockable_domains.json`**:
    *   **Description**: Sent to BSA (`bsaAddUnblockableDomainsUrl`) declaring
        unblockable domains.
    *   **Format**: JSON object grouping lists of FQDNs by lowercase reason
        (`"registered"`, `"reserved"`, `"invalid"`).
    *   **Example**:
        ```json
        {
          "registered": [
            "waymo.day"
          ],
          "reserved": [
            "waymo.ing",
            "waymo.app",
            "waymo.dev",
            "waymo.new",
            "waymo.page"
          ]
        }
        ```

6.  **`completed_orders.json`**:
    *   **Description**: Sent to BSA (`bsaOrderStatusUrl`) declaring completion
        of order processing.
    *   **Format**: JSON array of objects with `blockOrderId` (number) and
        `status` (`"Active"` for created orders or `"Closed"` for deleted
        orders).
    *   **Example**:
        ```json
        [
          {
            "blockOrderId": 2431667113971,
            "status": "Active"
          }
        ]
        ```

### Files Generated During Refresh Processing (`BsaRefreshAction`)

Folder: `gs://<bsaGcsBucket>/<refreshJobName>/`
(e.g., `gs://domain-registry-bsa/2026-10-26T15:45:00.916Z-refresh/`)

1.  **`refreshed_unblockable_domains.csv`**:
    *   **Description**: Unblockable domain lifecycle transitions identified by
        `DomainsRefresher`.
    *   **Format**: Headerless CSV;
        `<domainName>,<oldReason>,<newReasonOrPlaceholder>`.
    *   **Values**: The third column is either the new reason (`REGISTERED`,
        `RESERVED`) or `IS_DELETE` if the domain is no longer unblockable
        (i.e., became blockable).
    *   **Example**:
        ```csv
        nvidia.meme,REGISTERED,IS_DELETE
        ```

2.  **`removed_unblockable_domains.json`**:
    *   **Description**: Sent to BSA (`bsaRemoveUnblockableDomainsUrl`)
        reporting domains that became blockable or changed reason.
    *   **Format**: JSON array of domain name strings.
    *   **Example**:
        ```json
        [
          "nvidia.meme"
        ]
        ```

3.  **`added_unblockable_domains.json`**:
    *   **Description**: Sent to BSA (`bsaAddUnblockableDomainsUrl`) reporting
        newly unblockable domains or domains re-added after a reason change.
    *   **Format**: Same format as in download processing (reason to domain
        list map).

## 3. Download Processing (BsaDownloadAction)

The download action (`BsaDownloadAction`, path `/_dr/task/bsaDownload`,
scheduled hourly at minute 0) downloads the latest block lists from BSA,
identifies incremental differences compared to the previously completed
download, applies updates to local database tables, and exchanges status reports
with BSA REST API endpoints.

### Scheduling, Preconditions, and Resilience

Before processing commences, `BsaDownloadAction` executes several guard checks:

1.  **Distributed Locking**: Acquires `BsaLock` (`all-bsa-jobs`). If another
    BSA action (such as a download or refresh) is currently running, the job
    terminates gracefully and sends an email notification.
2.  **BSA Enrollment Check**: Verifies that at least one `REAL` TLD has active
    BSA enrollment (`Tlds.hasActiveBsaEnrollment(now)`). If none are enrolled,
    the action terminates immediately.
3.  **Conflict Prevention**: `DownloadScheduler.schedule()` checks whether an
    ongoing `BsaDomainRefresh` job is executing. If so, download scheduling is
    deferred until the refresh finishes.
4.  **Checkpointing and Resumption**: Download jobs progress through discrete
    stages represented by `DownloadStage`. Each stage is committed to the
    `BsaDownload` table upon completion. If an action fails mid-process (e.g.,
    due to a network timeout or instance restart), the next cron invocation
    skips already completed stages and resumes execution from the persisted
    checkpoint.

---

### Processing Stages and Execution Lifecycle

When a download job runs, it traverses the following stages in sequence:

#### Stage 1: `DOWNLOAD_BLOCK_LISTS`
*   **Action**: Fetches both `BLOCK` and `BLOCK_PLUS` product lists from BSA
    endpoints using `BlockListFetcher` via HTTPS `GET` with Bearer token
    authentication (`BsaCredential`).
*   **Inline Checksum Extraction**: `LazyBlockList` reads the BSA-generated
    checksum from the first line of the HTTP response.
*   **Unchanged Checksum Check (NOP)**: Compares the fetched checksums against
    the checksums from the latest completed download:
    *   If the checksums match and the elapsed time since the last download has
        not exceeded `bsaMaxNopInterval`, the download is discarded. The job
        transitions to the terminal stage `NOP`, saving bandwidth and CPU.
    *   If the checksums match but `bsaMaxNopInterval` has elapsed, processing
        continues to force a full re-evaluation.
*   **GCS Storage and Digest Computation**: Streams both files (`BLOCK.csv` and
    `BLOCK_PLUS.csv`) to GCS under `gs://<bsaGcsBucket>/<jobName>/`. While
    writing to GCS, `GcsClient` computes the cryptographic digest of each file
    body using `bsaChecksumAlgorithm` (e.g., SHA-256).
*   **Checksum Verification**: The computed digest is verified against the
    BSA inline checksum. If they differ, the job records the error, transitions
    to `CHECKSUMS_DO_NOT_MATCH`, and halts. Otherwise, the stage is updated to
    `MAKE_ORDER_AND_LABEL_DIFF`.

#### Stage 2: `MAKE_ORDER_AND_LABEL_DIFF`
*   **Action**: Invokes `BsaDiffCreator.createDiff()` to compare the newly
    downloaded block lists against the previous completed download's lists.
*   **Memory Optimization**: To process hundreds of thousands of labels within
    App Engine / GKE memory constraints, canonical order ID instances
    (`Canonicals<Long>`) and `ArrayList`-backed multimaps are used, keeping
    memory footprint well below 100 MB.
*   **Diff Classification**:
    *   **Orders**:
        *   `CREATE`: Order IDs present in the current download but not in the
            previous one.
        *   `DELETE`: Order IDs present in the previous download but absent from
            the current one.
    *   **Labels**:
        *   `CREATE`: Labels appearing in the current download that did not
            exist previously.
        *   `DELETE`: Labels present previously but missing in the new download.
        *   `NEW_ORDER_ASSOCIATION`: Existing labels that have been associated
            with one or more new block orders.
*   **IDN Support Mapping**: For each label, `IdnChecker` queries all supported
    IDN tables across BSA-enrolled TLDs (`getAllValidIdns(label)`).
*   **GCS Output**: Writes `orders_diff.csv` and `labels_diff.csv` to GCS, then
    updates stage to `APPLY_ORDER_AND_LABEL_DIFF`.

#### Stage 3: `APPLY_ORDER_AND_LABEL_DIFF`
*   **Action**: Reads `labels_diff.csv` (from the in-memory diff or from GCS)
    and applies changes to the database in batches of `bsaTxnBatchSize` (e.g.,
    500) within `TRANSACTION_REPEATABLE_READ` transactions via
    `LabelDiffUpdates.applyLabelDiff()`.
*   **Database Updates**:
    *   **New Labels (`CREATE`)**: Inserts new `BsaLabel` entities for labels
        supported by at least one enrolled TLD.
    *   **Deleted Labels (`DELETE`)**: Deletes records from `BsaLabel`. Database
        foreign key cascades automatically delete associated
        `BsaUnblockableDomain` rows.
    *   **New Order Associations (`NEW_ORDER_ASSOCIATION`)**: Verifies that the
        label already exists in `BsaLabel`.
*   **Unblockable Domain Identification**:
    *   Identifies all domains matching new labels across enrolled TLDs:
        *   **Registered**: Checked against the `Domain` table; matching live
            domains are inserted into `BsaUnblockableDomain` with reason
            `REGISTERED`.
        *   **Reserved**: Checked against reserved lists; matching reserved
            names are inserted into `BsaUnblockableDomain` with reason
            `RESERVED`.
        *   **Invalid**: TLDs that do not support the label's IDN table are
            marked as `INVALID` (not saved in the database, but tracked for
            reporting).
*   **GCS Output**: Writes all discovered unblockable domains to
    `unblockable_domains.csv` on GCS, then updates stage to
    `REPORT_START_OF_ORDER_PROCESSING`.

#### Stage 4: `REPORT_START_OF_ORDER_PROCESSING`
*   **Action**: Reads `orders_diff.csv` from GCS.
*   **Payload Construction**: Generates a JSON order status report via
    `JsonSerializations.toInProgressOrdersReport()`, setting status to
    `"ActivationInProgress"` for `CREATE` orders and `"ReleaseInProgress"` for
    `DELETE` orders.
*   **BSA Notification**: If order changes exist, saves
    `in_progress_orders.json` to GCS and transmits the payload via HTTP `POST`
    to `bsaOrderStatusUrl`.
*   **Transition**: Updates job stage to
    `UPLOAD_UNBLOCKABLE_DOMAINS_FOR_NEW_ORDERS`.

#### Stage 5: `UPLOAD_UNBLOCKABLE_DOMAINS_FOR_NEW_ORDERS`
*   **Action**: Reads `unblockable_domains.csv` from GCS.
*   **Payload Construction**: Generates a JSON unblockable domains report via
    `JsonSerializations.toUnblockableDomainsReport()`, organizing domain names
    under lowercase reasons (`"registered"`, `"reserved"`, `"invalid"`).
*   **BSA Notification**: If unblockable domains exist, saves
    `added_unblockable_domains.json` to GCS and transmits the payload via HTTP
    `POST` to `bsaAddUnblockableDomainsUrl`.
*   **Transition**: Updates job stage to `REPORT_END_OF_ORDER_PROCESSING`.

#### Stage 6: `REPORT_END_OF_ORDER_PROCESSING`
*   **Action**: Reads `orders_diff.csv` from GCS.
*   **Payload Construction**: Generates the final completed orders report via
    `JsonSerializations.toCompletedOrdersReport()`, setting status to
    `"Active"` for created orders and `"Closed"` for deleted orders.
*   **BSA Notification**: If order changes exist, saves `completed_orders.json`
    to GCS and transmits the payload via HTTP `POST` to `bsaOrderStatusUrl`.
*   **Transition**: Updates job stage to the terminal stage `DONE`.

---

### Terminal Stages Summary

*   **`DONE`**: The download and all associated diffs, database mutations, and
    API reports succeeded completely.
*   **`NOP`**: Download skipped because block list checksums have not changed
    since the last completed job, and `bsaMaxNopInterval` has not elapsed.
*   **`CHECKSUMS_DO_NOT_MATCH`**: Processing halted because the checksum
    calculated on the downloaded CSV content did not match the checksum provided
    by BSA in the first line of the download.

---

### Database Tables Updated During Download Processing

During download processing, three database tables are modified:

#### 1. `BsaDownload`
*   **Purpose**: Tracks individual download jobs, recording their execution
    state, timestamps, and block list checksums.
*   **Lifecycle Updates**:
    *   **Job Creation**: Inserted by `DownloadScheduler.schedule()` with
        `stage = DOWNLOAD_BLOCK_LISTS` and empty checksums.
    *   **Stage Transitions**: Checkpointed at each stage transition:
        1.  `DOWNLOAD_BLOCK_LISTS` -> `MAKE_ORDER_AND_LABEL_DIFF` (sets
            `blockListChecksums`, e.g., `BLOCK=<hash>,BLOCK_PLUS=<hash>`).
        2.  `MAKE_ORDER_AND_LABEL_DIFF` -> `APPLY_ORDER_AND_LABEL_DIFF`.
        3.  `APPLY_ORDER_AND_LABEL_DIFF` -> `REPORT_START_OF_ORDER_PROCESSING`.
        4.  `REPORT_START_OF_ORDER_PROCESSING` ->
            `UPLOAD_UNBLOCKABLE_DOMAINS_FOR_NEW_ORDERS`.
        5.  `UPLOAD_UNBLOCKABLE_DOMAINS_FOR_NEW_ORDERS` ->
            `REPORT_END_OF_ORDER_PROCESSING`.
        6.  `REPORT_END_OF_ORDER_PROCESSING` -> `DONE`.
    *   **Terminal Alternatives**: May be set to `NOP` or
        `CHECKSUMS_DO_NOT_MATCH`.

#### 2. `BsaLabel`
*   **Purpose**: Stores the global set of second-level domain (SLD) labels
    currently subject to BSA blocks. EPP flows (`DomainCreateFlow`,
    `DomainCheckFlow`) query this table (cached via `BsaLabelUtils`) to block
    domain registrations in enrolled TLDs.
*   **Updates during `APPLY_ORDER_AND_LABEL_DIFF`**:
    *   **Insertions (`CREATE`)**: New labels valid in at least one enrolled
        TLD are inserted (`tm().putAll(...)`) with `label` as primary key and
        `creationTime` matching the job creation timestamp.
    *   **Deletions (`DELETE`)**: Labels no longer present in BSA block lists
        are removed via `DELETE FROM "BsaLabel" WHERE label IN (...)`.
    *   **New Associations (`NEW_ORDER_ASSOCIATION`)**: Validated to ensure
        the label already exists in the table (no row updates needed).

#### 3. `BsaUnblockableDomain`
*   **Purpose**: Records domains (`label` + `tld` composite key) that match an
    active `BsaLabel` but cannot be blocked because the domain is currently in
    use (reason `REGISTERED` or `RESERVED`).
*   **Updates during `APPLY_ORDER_AND_LABEL_DIFF`**:
    *   **Insertions**: When new labels (`CREATE`) are processed, Nomulus checks
        all enrolled TLDs supporting the label:
        *   If registered in the `Domain` table, inserted with reason
            `REGISTERED`.
        *   If present on the TLD's reserved lists and eligible for registration
            (e.g., via auth token or sunrise), inserted with reason `RESERVED`.
    *   **Cascade Deletions**: When a `BsaLabel` is deleted, all corresponding
        `BsaUnblockableDomain` rows are automatically deleted by PostgreSQL
        via the foreign key cascade constraint:
        ```sql
        ALTER TABLE ONLY public."BsaUnblockableDomain"
            ADD CONSTRAINT fkbsaunblockabledomainlabel
            FOREIGN KEY (label) REFERENCES public."BsaLabel"(label)
            ON DELETE CASCADE;
        ```

*(Note: Invalid domain names are not persisted in `BsaUnblockableDomain`; they
are only reported to the BSA API).*

## 4. Activity During a Refresh Action

The refresh action (`BsaRefreshAction`, path `/_dr/task/bsaRefresh`, scheduled
every 30 minutes) detects domain status changes that occur between hourly block
list downloads.

### Execution Workflow and Stages

1.  **Locking and Eligibility**:
    *   Acquires `BsaLock`. If another BSA task holds the lock, execution exits.
    *   Verifies that at least one TLD has active BSA enrollment.
    *   Calls `RefreshScheduler.schedule()`. If an ongoing `BsaDownload` is
        running, refresh waits. If no previous download has completed, refresh
        exits. Otherwise, it resumes an ongoing refresh or creates a new
        `BsaDomainRefresh` record (stage `CHECK_FOR_CHANGES`).

2.  **`CHECK_FOR_CHANGES` Stage**:
    `DomainsRefresher` compares database states between the previous refresh
    start time and current time:
    *   **Stale Unblockables (`refreshStaleUnblockables`)**: Iterates through
        `BsaUnblockableDomain` rows:
        *   `REGISTERED` domains no longer in the `Domain` table: If on a
            reserve list, changed to `RESERVED`; otherwise deleted (now
            blockable).
        *   `RESERVED` domains newly found in the `Domain` table: Changed to
            `REGISTERED`.
        *   `RESERVED` domains removed from reserve lists: Deleted (now
            blockable).
    *   **New Unblockables (`getNewUnblockables`)**:
        *   Queries domains created in BSA-enrolled TLDs since the previous
            refresh (`prevRefreshStartTime`), filtering for matches in
            `BsaLabel`.
        *   Queries all reserved domains on enrolled TLDs matching `BsaLabel`.
        *   Diffs against existing `BsaUnblockableDomain` entries to detect new
            additions or upgrades (reserved to registered).
    *   If no changes are found, transitions directly to `DONE`.
    *   If changes exist, writes `refreshed_unblockable_domains.csv` to GCS and
        updates stage to `APPLY_CHANGES`.

3.  **`APPLY_CHANGES` Stage**:
    *   Reads `refreshed_unblockable_domains.csv` from GCS.
    *   In batches of 500, transacts updates to `BsaUnblockableDomain`:
        *   Deletes records marked as `IS_DELETE`.
        *   Upserts records marked with new reasons (`REGISTERED` or
            `RESERVED`).
    *   Updates stage to `UPLOAD_REMOVALS`.

4.  **`UPLOAD_REMOVALS` Stage**:
    *   Reads `refreshed_unblockable_domains.csv` from GCS.
    *   Filters changes matching `isChangeOrDelete()` (domains that became
        blockable, as well as domains changing reason).
    *   *Note*: BSA API requires domains changing reason (e.g., `RESERVED` to
        `REGISTERED`) to be removed before being re-added.
    *   If any exist, generates `removed_unblockable_domains.json`, saves it to
        GCS, and sends it via HTTP `POST` to `bsaRemoveUnblockableDomainsUrl`.
    *   Updates stage to `UPLOAD_ADDITIONS`.

5.  **`UPLOAD_ADDITIONS` Stage**:
    *   Reads `refreshed_unblockable_domains.csv` from GCS.
    *   Filters changes matching `isNewOrChange()` (new unblockables and
        re-added reason transitions).
    *   If any exist, generates `added_unblockable_domains.json`, saves it to
        GCS, and sends it via HTTP `POST` to `bsaAddUnblockableDomainsUrl`.
    *   Updates stage to `DONE`.

## 5. Activity During a Validate Action

The validate action (`BsaValidateAction`, path `/_dr/task/bsaValidate`,
scheduled twice daily at 09:50 and 21:50 UTC) verifies that local database
tables remain consistent with raw GCS block lists, active domains, and reserve
lists.

### Validation Checks Performed

1.  **Initialization**:
    *   Fetches the job name of the latest completed `BsaDownload` from the
        database (`fetchMostRecentDownloadJobIdIfCompleted`).

2.  **`checkBsaLabels` (Label Integrity)**:
    *   Reads all labels from `BLOCK.csv` and `BLOCK_PLUS.csv` in GCS for the
        latest download job, filtering for labels supported by IDN tables.
    *   Batches through all labels stored in the `BsaLabel` table.
    *   Computes two set differences:
        *   **Missing Labels**: Labels present in downloaded files but missing
            from `BsaLabel`.
        *   **Unexpected Labels**: Labels present in `BsaLabel` that do not
            exist in the downloaded files.
    *   Any discrepancy is recorded as an error with sample labels.

3.  **`checkWronglyReportedUnblockableDomains` (False Positives/Reason Drift)**:
    *   Batches through all persisted `BsaUnblockableDomain` rows.
    *   Computes each domain's expected blockability status against live data:
        active registration in `Domain`, presence in `ReservedList`, or invalid
        IDN.
    *   If the database reason does not match expected reason:
        *   Allows recent registrations within `bsaValidationMaxStaleness`
            (e.g., 1 hour) to account for transactional propagation delay.
        *   Otherwise logs an error (e.g.,
            `example.tld: should be RESERVED, found REGISTERED` or
            `example.tld: should be BLOCKABLE, found REGISTERED`).

4.  **`checkMissingUnblockableDomains` (False Negatives)**:
    *   **Missing Registered Domains**: Executes native SQL
        (`queryMissedRegisteredUnblockables`) across all BSA-enrolled TLDs to
        find active registered domains matching `BsaLabel` that lack a
        `REGISTERED` entry in `BsaUnblockableDomain`. Any domain older than
        `maxStaleness` is flagged.
    *   **Missing Reserved Domains**: Loads all reserved domain names across
        enrolled TLDs that match `BsaLabel` (`isLabelBlocked`) and verifies that
        each is present in `BsaUnblockableDomain` with reason `REGISTERED` or
        `RESERVED`.

5.  **Notification**:
    *   If any errors are encountered, an alert email containing the detailed
        discrepancy list is sent to administrators via `BsaEmailSender`.

## 6. UploadBsaUnavailableDomainsAction

`UploadBsaUnavailableDomainsAction` (path `/_dr/task/uploadBsaUnavailableNames`,
scheduled twice daily at 08:23 and 20:23 UTC) compiles and transmits a complete,
authoritative list of all unavailable domain names across all BSA-enrolled TLDs
to BSA.

### Purpose and Operation

Unlike the incremental diffs and unblockable reports produced during downloads
and refreshes, this action provides a full snapshot of all domain names on
enrolled TLDs that cannot be blocked because they are registered, reserved, or
both.

### Step-by-Step Workflow

1.  **Querying Unavailable Domains**:
    *   Identifies all `REAL` TLDs currently enrolled with BSA
        (`isEnrolledWithBsa`).
    *   Queries the Cloud SQL read replica (`replicaTm()`) to prevent read
        contention on the primary database:
        *   **Reserved Names**: Loads all reserved lists configured on the
            enrolled TLDs and constructs FQDNs for all entries.
        *   **Registered Names**: Queries active domains (`deletionTime > now`)
            in batches of 40,000 ordered by domain name.
    *   Combines all names into an `ImmutableSortedSet<String>` (natural ASCII
        ordering, punycoded FQDNs).

2.  **Archiving to GCS**:
    *   Writes the full, uncompressed domain list to GCS in the bucket specified
        by `bsaUnavailableDomainsGcsBucket`.
    *   Filename format: `unavailable_domains_<runTime>.txt` (US-ASCII encoded,
        newline-delimited, trailing newline).
    *   This serves as an audit record of the uploaded data.

3.  **Streaming Multipart Upload to BSA**:
    *   Calculates a SHA-512 checksum across all domain lines in the set:
        `Hashing.sha512().newHasher().putString(name + "\n", UTF_8)`.
    *   Constructs an HTTP `POST` multipart form request (`MultipartBody.FORM`)
        sent to `bsaUploadUnavailableDomainsUrl` with an `Authorization: Bearer`
        header:
        *   **Form Part `"zone"`**: A JSON payload containing the SHA-512 hash:
            ```json
            {"checkSum": "<sha512_hex_string>"}
            ```
        *   **Form Part `"file"`**: The domain list compressed with gzip
            (`unavailable_domains_<runTime>.txt.gz`).
    *   **Memory Efficiency**: To stream large lists without exhausting JVM heap
        memory, a background thread pipes data through a `PipedOutputStream`
        into a `GZIPOutputStream`, connected to a `PipedInputStream` consumed by
        a custom `StreamingRequestBody`.

4.  **Operator Notification**:
    *   Sends an email notification via `BsaEmailSender` reporting whether the
        upload completed successfully or failed.
